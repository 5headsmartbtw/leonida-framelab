# VIctory as a FrameLab consumer

Read-only audit of [VIctory at `ffe310eb2098e52169f4c44db5ffdabf43a72622`](https://github.com/Marvisak/VIctory/tree/ffe310eb2098e52169f4c44db5ffdabf43a72622). The GPU crate is under `crates/victory-gpu` at this revision. No game files or captured inputs are required for this analysis.

| Area | Observed source | Integration requirement |
| --- | --- | --- |
| Device and submission | The host creates a D3D12 fence and queue. It replays deferred work before calling `ExecuteCommandLists`, then signals a monotonically increasing fence and waits on an event. A Signal/SetEvent failure is logged. [host.rs device](https://github.com/Marvisak/VIctory/blob/ffe310eb2098e52169f4c44db5ffdabf43a72622/crates/victory-gpu/src/host.rs#L185-L225) · [host submission](https://github.com/Marvisak/VIctory/blob/ffe310eb2098e52169f4c44db5ffdabf43a72622/crates/victory-gpu/src/host.rs#L503-L545) | Use the real host command queue, verified fence identity and value. A warning path cannot retire a FrameLab packet as if the wait had succeeded. The console-facing signal/wait shims are separate. [queue.rs](https://github.com/Marvisak/VIctory/blob/ffe310eb2098e52169f4c44db5ffdabf43a72622/crates/victory-gpu/src/queue.rs#L147-L169) |
| Texture ownership | `HostTexture` carries an `ID3D12Resource` and tracked state. The title resource can own an `Arc<HostTexture>`, and command lists can pin cloned owners. `host_resource` exposes a borrowed resource and `host_copy` supplies a clone. [resource.rs](https://github.com/Marvisak/VIctory/blob/ffe310eb2098e52169f4c44db5ffdabf43a72622/crates/victory-gpu/src/resource.rs#L741-L798) | Keep a real Arc/COM owner, stable identity and resource generation through the final fence. Resolve renderer state under the existing host protocol. A raw pointer or a guest handle alone does not pin an allocation. |
| Present | The queue presents the first resource of the first plane. It resolves its host texture, updates the tracked copy state and restores it after host Present. The host Presenter lazily creates/resizes its swapchain, records a copy and barriers, submits and calls DXGI Present. [queue.rs](https://github.com/Marvisak/VIctory/blob/ffe310eb2098e52169f4c44db5ffdabf43a72622/crates/victory-gpu/src/queue.rs#L278-L296) · [host.rs](https://github.com/Marvisak/VIctory/blob/ffe310eb2098e52169f4c44db5ffdabf43a72622/crates/victory-gpu/src/host.rs#L1590-L1668) | First seam to evaluate is after input ownership and state resolve, before the final copy. Preserve normal Present, resize, source frame accounting and state restoration. Count generated Presents separately. |
| Temporal semantics | The reviewed Present path passes color, prior tracked state and frame counter. It does not provide a matched depth/MV/camera/jitter packet. | A versioned producer must verify how each GPU input maps to the same source frame, including motion and jitter conventions. Keep unknown semantics unavailable. |

AwkGrep256's [#730](https://github.com/Marvisak/VIctory/issues/730) reports host D3D12 AMD upscaler context creation and a memory budget limitation at 4K, with in-world upscaling untested in that report. [#944](https://github.com/Marvisak/VIctory/issues/944) reports an AMD experiment under Proton on RX 9070 XT. The author observed three additional Presents from three rendered frames once depth and motion data arrived, with mostly black world rendering and a reported GPU reset in one configuration. These are author-reported AMD experiments in separate branches. They do not establish NVIDIA compatibility or a validated seam in the audited main revision.

The first integration experiment should use an independently authored Rust synthetic producer. It needs the FrameLab D3D12 dispatch and ABI layout/lifetime checks before connecting to a VIctory Presenter. Use a real host fence, test cancellation, resize and lease release, and record SR-only and FG-only results separately.
